# Игропоиск — Review Module / Review Skill v1

**Статус:** WORKING / DRAFT  
**Зафиксировано:** 2026-09-04  
**Назначение:** рабочий контракт генерации полноформатных редакционных обзоров игр.

## Граница модуля

Обзор — отдельная review/editorial-подсистема. Он может быть встроен в страницу игры, но не является обязательной частью Game Page Module и не блокирует создание или публикацию страницы игры.

Review Module обязан использовать канонический корпус источников страницы игры из `data/game-sources/<slug>.json` и каноническую идентичность игры через Game Registry / `game_id`. Параллельный независимый review-source registry не создаётся.

Канонические границы модуля страницы игры определены в `docs/GAME_PAGE_MODULE_STABLE.md`. Общая архитектура проекта — в `docs/SYSTEM_ARCHITECTURE.md`.

## Цель Review Skill v1

Создавать длинный редакционный обзор Игропоиска, который:

- основан на уже собранном source corpus;
- фактически точен и не смешивает версии игры;
- написан естественным русским журнальным языком;
- остаётся актуальным через годы и не привязан к текущему календарному году;
- объясняет, чем именно эта игра интересна, как работают её ключевые системы и почему они создают определённое впечатление;
- использует конкретные детали вместо общих фраз;
- честно обсуждает недостатки без обязательной рамки «игра устарела»;
- строит структуру из характера конкретной игры, а не из универсального шаблона;
- заканчивается осмысленным выводом, а не пересказом предыдущих разделов.

Ориентир по объёму: примерно 2 000–2 600 слов, если конкретная игра не требует иного объёма.

## Главный редакционный принцип: писать про игру, а не про текущий год

Обзор должен быть evergreen.

Нельзя автоматически строить анализ из позиции «мы сейчас смотрим на старую игру». Возраст игры — только один из возможных контекстов и используется лишь тогда, когда он действительно объясняет дизайн, технологию или историческую роль.

Допустимо:

- «Для игры 1992 года такая скорость и подача были необычными»;
- «На момент выхода Autolog был одним из заметных нововведений»;
- сравнение конкретного дизайнерского решения с более поздними подходами, если это помогает понять саму игру.

Не допускается как системный приём:

- отдельный обязательный раздел «Что устарело»;
- «как игра ощущается сегодня»;
- «что она потеряла за N лет»;
- оценка каждой старой механики только через современную точку отсчёта;
- фразы, делающие статью зависимой от даты публикации.

Если у игры есть проблема, нужно называть саму проблему: однообразные лабиринты, неудобный инвентарь, слабая обратная связь, неточная стрельба, затянутые повторы, пиксель-хантинг, грубая камера и т. п.

## Источники и доказательная база

Review Module не пишет из общей памяти модели.

Для каждой игры используется канонический source corpus страницы игры. Перед написанием модель должна извлечь из него evidence по категориям:

- центральная игровая фантазия;
- сюжет и персонажи;
- ключевые механики;
- структура уровней / мира / кампании;
- интерфейс и обратная связь;
- управление;
- AI и поведение систем;
- визуальный стиль;
- музыка и звук;
- характерные детали и запоминающиеся моменты;
- сильные стороны;
- недостатки и спорные решения;
- исторический контекст, только если он полезен;
- точная версия игры и отличия от ремастеров, портов, ремейков или сиквелов, если это необходимо для исключения смешения фактов.

Факт может попасть в обзор только если он подтверждается source corpus либо является явно маркированным редакционным выводом, непосредственно вытекающим из подтверждённых фактов.

Нельзя добавлять вымышленные детали ради атмосферы.

В опубликованном тексте не должно быть служебного языка вроде «источники утверждают», «по данным корпуса», «в evidence найдено». Источники определяют факты, но статья должна читаться как цельная редакционная работа. Публичный список источников может отображаться отдельно на странице обзора/игры.

## Review Skill v1 — четыре прохода

### Pass 1. Evidence extraction

Из source corpus извлекается не пересказ материалов, а карта доказательств.

Особое внимание уделяется характерным деталям, которые делают игру узнаваемой. Например:

- лицо Бласковица в HUD, которое меняется по мере потери здоровья;
- отдача и перезарядка дробовика в Dangerous Dave;
- физика «Мако» в Mass Effect;
- Autolog в Hot Pursuit;
- поведение полиции, светофоры и поездки в Mafia.

Такие детали важнее универсальных фраз вроде «игра обладает атмосферой».

### Pass 2. Editorial angle & structure

До написания текста модель определяет 6–10 смысловых аспектов, которые лучше всего объясняют именно эту игру.

Структура не должна быть универсальной. Запрещён обязательный шаблон:

`сюжет → геймплей → графика → что устарело → итог`.

Для каждой игры структура строится заново.

Пример принципа:

- Mafia: герой → персонажи → город → автомобили → миссии → стрельба → конкретные проблемы → музыка/визуальный стиль → итог;
- Wolfenstein 3D: скорость → враги → лабиринты → секреты → HUD/обратная связь → оружие/звук → боссы → ограничения → итог;
- Jack Orlando: расследование → город → персонажи → логика загадок → художественная постановка → музыка → конкретные проблемы → итог.

Заголовки должны одновременно:

1. ясно показывать, о каком аспекте идёт речь;
2. содержать тезис или интригу, если это не ухудшает ясность;
3. не повторять друг друга по смыслу;
4. позволять понять общий маршрут статьи только по левому меню/оглавлению.

Хороший заголовок: `Когда начинается стрельба, Mafia перестаёт быть романтичной`.

Плохой заголовок: `Что сегодня мешает сильнее всего` — неясно, о чём раздел и зачем он существует.

### Pass 3. Draft

Текст пишется нормальной журнальной прозой.

Правила:

- полноценные абзацы;
- не превращать прозу в цепочку коротких предложений с новой строки;
- короткая строка или одно предложение отдельным абзацем допустимы только как редкий осмысленный акцент;
- каждый раздел раскрывает один основной аспект;
- конкретный пример предпочтительнее абстрактного тезиса;
- авторская оценка допустима и желательна, но должна быть понятной и обоснованной;
- умеренный юмор допустим, если он органичен;
- статья не должна звучать как инструкция, энциклопедия или пересказ пресс-релиза;
- вступление должно быстро вводить в саму игру, сцену, героя или центральное ощущение, а не начинаться с сухой исторической справки;
- недостатки обсуждаются там, где они логически относятся к системе, либо в отдельном разделе только если у игры действительно есть самостоятельный крупный пласт проблем;
- не создавать отдельную тему про возраст игры просто ради баланса «плюсы/минусы».

## Интерфейс и обратная связь — обязательный объект проверки

Перед финализацией обзор обязан проверить, есть ли в source corpus интересные сведения про:

- HUD;
- отображение здоровья;
- карту и навигацию;
- инвентарь;
- сохранения / checkpoints;
- индикаторы оружия и боеприпасов;
- визуальные и звуковые сигналы;
- меню и способ взаимодействия;
- необычные элементы обратной связи.

Если такая деталь помогает понять игру, она должна конкурировать за место в статье наравне с сюжетом, графикой и основными механиками.

Не пропускать характерную деталь только потому, что она «слишком маленькая» для стандартного обзора.

## Как писать о недостатках

Минусы нужны, но не должны существовать как ритуальный раздел.

Предпочтительный порядок:

1. назвать конкретную систему;
2. объяснить, что именно в ней работает хуже;
3. показать, как это влияет на игру;
4. при необходимости дать контекст;
5. не превращать вывод в общую фразу «игра состарилась».

Примеры:

Плохо: `В бою Mass Effect сегодня выдаёт свой возраст гораздо быстрее, чем в диалогах.`

Лучше: `Перестрелкам Mass Effect не хватает веса: оружие ощущается слабо, укрытия работают грубо, а часть столкновений скорее мешает добраться до следующего сюжетного эпизода.`

Плохо: `Что Wolfenstein 3D потерял за тридцать лет.`

Лучше: `Лабиринты и однообразие уровней` или более точный заголовок, соответствующий реальному содержанию раздела.

## Pass 4. Anti-generic / evergreen audit

После черновика выполняется отдельный редакционный аудит.

Проверить:

- нет ли фраз, привязывающих статью к текущему году без необходимости;
- нет ли универсального блока «что устарело»;
- названы ли конкретные недостатки вместо абстрактной старости;
- не повторяют ли разделы друг друга;
- можно ли понять структуру статьи только по заголовкам;
- не пропущены ли характерные детали из evidence;
- нет ли длинных абзацев общей похвалы без примеров;
- нет ли искусственной драматизации короткими строками;
- нет ли сухой энциклопедической подачи;
- не начал ли текст объяснять процесс работы модели или источников;
- не смешаны ли версии игры;
- не повторяет ли финал содержание всех разделов;
- остаётся ли статья естественной, если её прочитают через много лет.

Если аудит находит нарушение, исправление выполняется той же моделью и только на основании того же source corpus.

## Языковой blacklist

Следующие формулировки и близкие к ним конструкции считаются подозрительными и требуют замены, если для них нет конкретной причины:

- `состарилось плохо`;
- `выдаёт свой возраст`;
- `сегодня ощущается`;
- `по современным меркам`;
- `по современным стандартам`;
- `для современного игрока`;
- `что игра потеряла за N лет`;
- `спустя N лет это...` как универсальный заход;
- `игрово`;
- `положенное на рельсы путешествие`;
- служебные AI-формулировки и мета-комментарии о написании обзора.

Blacklist не запрещает исторический анализ. Он запрещает ленивую временную рамку вместо анализа самой игры.

## Времена глаголов и действующие механики

Если механика существует внутри игры, о ней следует писать в настоящем времени независимо от года выхода.

Плохо: `Одной из важных идей Hot Pursuit был Autolog.`

Лучше: `Autolog связывает одиночную карьеру с результатами друзей.`

Историческую роль можно добавить отдельным предложением: `На момент выхода это было одним из самых заметных нововведений игры.`

То же правило применяется к HUD, системам боя, AI, структуре уровней и другим действующим элементам игры.

## Принцип отбора материала

Review Module не обязан использовать всё, что найдено в source corpus.

Каждый фрагмент проходит вопрос:

**Помогает ли эта деталь понять, почему именно эта игра такая?**

Если нет — её можно удалить независимо от числа источников, в которых она встречается.

Часто одна конкретная характерная деталь ценнее нескольких общих тезисов.

## Финал обзора

Финал не является сводкой `плюсы / минусы` и не должен просто повторять каждый раздел.

Он должен:

- собрать главный характер игры в одну мысль;
- показать, почему опыт остаётся цельным несмотря на недостатки;
- при необходимости вернуться к образу или ситуации из начала статьи;
- оставить эмоциональное или интеллектуальное послевкусие;
- после этого дать итоговую оценку Игропоиска.

Допустима короткая итоговая формулировка после оценки, но она должна быть выводом, а не рекламным слоганом.

## Golden references

Текущая переработанная `Mafia: The City of Lost Heaven` используется как первый golden editorial reference для структуры, естественного русского, конкретных наблюдений и финального послевкусия.

Следующий набор редакционных примеров для проверки правил:

- Dangerous Dave in the Haunted Mansion;
- Far Cry;
- Jack Orlando: A Cinematic Adventure;
- Mass Effect (2007);
- Wolfenstein 3D;
- Need for Speed: Hot Pursuit (2010).

Эти тексты пока являются рабочими примерами, а не автоматически утверждёнными golden reviews. Замечания по ним должны использоваться для уточнения этого skill до финальной фиксации.

## Один model-owner на обзор

Один полный обзор создаётся одной утверждённой моделью end-to-end.

Допустима многошаговая генерация, но все шаги выполняет одна и та же модель:

1. evidence extraction;
2. editorial angle & structure;
3. draft / sectional generation;
4. synthesis and polish;
5. anti-generic / evergreen audit.

При технической ошибке допускается повтор той же модели. Другая модель не продолжает и не заменяет текст в рамках того же обзора.

## Publication gate

Обзор не публикуется, если:

- есть неподтверждённый существенный факт;
- смешаны разные версии игры;
- есть source/process leakage;
- структура повторяется или неясна по заголовкам;
- значимая часть текста построена на временной рамке `сегодня / спустя N лет` без содержательной причины;
- проза распалась на искусственные короткие строки;
- текст заметно шаблонный и может быть без существенных изменений перенесён на другую игру;
- финал является механическим пересказом разделов;
- качество существенно ниже принятого golden reference.

Отсутствие готового обзора не блокирует публикацию страницы игры.
