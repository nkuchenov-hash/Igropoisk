# Пилот ручного аудита «Игропоиск Топ-250»

## Статус и границы пилота

«Игропоиск Топ-250» — внутренний рейтинг, а не готовый публичный раздел сайта. Этот пилот нужен только для ручной проверки первых 20 популярных игр и принятия редакционного решения: какие из них подходят для полноценного обзора.

Пилот **не меняет** код приложения, алгоритм рейтинга, источники данных, UI, CI/CD, правила публикации или существующий пайплайн генерации обзоров. Он использует уже существующие данные и результаты пайплайна как вход для ручной проверки.

## Цель

На фиксированном списке из 20 наиболее популярных игр проверить, насколько текущие данные и материалы позволяют запускать полноценный обзор без автоматического массового запуска по всему рейтингу.

Результат пилота — по каждой из 20 игр должно быть одно зафиксированное решение:

- `review` — игру можно передавать в существующий пайплайн полноценного обзора;
- `hold` — обзор пока не запускать, пока не устранён конкретный блокер;
- `exclude` — игру не следует брать в этот пилот обзоров; причина обязательна.

Эти статусы относятся только к пилоту ручного аудита и не изменяют рейтинг или каталог.

## Роли

### Владелец пилота

Утверждает границы проверки, итоговые решения и спорные случаи. Не меняет рейтинг в рамках этого пилота.

### Ревьюер

Последовательно проверяет все 20 игр по единому чек-листу, фиксирует решение, причины, найденные проблемы и ссылки/пути к имеющимся материалам.

### Оператор пайплайна

После утверждения результата может передать игры со статусом `review` в уже существующий пайплайн генерации обзоров. Сам пилот не запускает и не изменяет этот пайплайн.

Один человек может совмещать роли; в отчёте всё равно фиксируется, кто выполнил аудит и кто утвердил результат.

## Вход пилота

Перед началом аудита нужно зафиксировать:

1. дату и время снимка;
2. commit SHA / версию данных, на которых сформирован список;
3. точный список топ-20 в исходном порядке;
4. доступные для каждой игры идентификаторы и существующие материалы.

Список не пересортировывается вручную. Если во входных данных обнаружена неоднозначность, дубликат, отсутствующий идентификатор или другая проблема качества данных, она записывается в отчёт и не скрывается ручной корректировкой.

## Пошаговый процесс

1. **Зафиксировать вход.** Сохранить источник топ-20, commit SHA и порядок игр на момент начала проверки.
2. **Создать рабочий отчёт.** Скопировать `docs/templates/top-250-review-report.md` и заполнить метаданные пилота.
3. **Проверить состав.** Убедиться, что в отчёте ровно 20 позиций и каждая позиция соответствует исходному списку.
4. **Проверить каждую игру.** Пройти чек-лист ниже без изменения исходных данных.
5. **Зафиксировать решение.** Для каждой игры выбрать только `review`, `hold` или `exclude` и указать причину.
6. **Зафиксировать блокеры и проблемы данных.** Не исправлять их внутри пилота незаметно; записать их как отдельные наблюдения.
7. **Подвести итог.** Посчитать количество `review`, `hold`, `exclude` и перечислить общие причины блокировки.
8. **Ручное утверждение.** Владелец пилота подтверждает итоговый отчёт до передачи любых игр в существующий обзорный пайплайн.

## Чек-лист для каждой игры

### Идентичность

- [ ] Игра однозначно идентифицирована в существующих данных.
- [ ] Нет неразрешённого дубликата или конфликта идентификаторов.
- [ ] Проверяемая сущность действительно соответствует игре из исходного топ-20.

### Данные и материалы

- [ ] Есть достаточно существующих данных, чтобы редактор мог понять, о какой игре идёт речь и что именно будет обозреваться.
- [ ] Критичные пробелы, противоречия или сомнительные данные перечислены явно.
- [ ] Доступные исследовательские/редакционные материалы и их пути или ссылки зафиксированы.

### Пригодность для полноценного обзора

- [ ] Нет очевидного конфликта с уже существующим обзором или другой редакционной сущностью.
- [ ] Ревьюер может сформулировать, почему игра подходит или не подходит для полноценного обзора сейчас.
- [ ] Для `hold` указан конкретный блокер и условие, после которого игру можно пересмотреть.
- [ ] Для `exclude` указана конкретная причина исключения.

### Аудит решения

- [ ] Выбран ровно один статус: `review`, `hold` или `exclude`.
- [ ] Решение имеет краткое обоснование.
- [ ] Все обнаруженные проблемы качества данных сохранены в отчёте, а не исправлены молча.

## Критерии приёмки пилота

Пилот считается завершённым, когда одновременно выполнены все условия:

1. Проверены ровно 20 игр из зафиксированного исходного списка и сохранён их исходный порядок.
2. Для каждой игры заполнен чек-лист и указан один итоговый статус.
3. Для каждого `hold` и `exclude` указана конкретная причина; для `review` зафиксировано, что критичных блокеров не найдено.
4. Все найденные неоднозначности, дубликаты и проблемы качества данных перечислены в отчёте.
5. В отчёте есть итоговые количества по трём статусам и список общих блокеров.
6. Итог вручную утверждён владельцем пилота.
7. В рамках работы не изменялись код приложения, рейтинг, источники данных, UI, CI/CD или production-поведение.

## Формат отчёта

Использовать шаблон `docs/templates/top-250-review-report.md`.

Минимально отчёт должен содержать:

- метаданные снимка и commit SHA;
- имя ревьюера и утверждающего;
- таблицу всех 20 игр в исходном порядке;
- идентификатор и название игры;
- доступное значение внутреннего рейтинга/популярности без его пересчёта;
- решение `review` / `hold` / `exclude`;
- краткое обоснование;
- блокеры и проблемы качества данных;
- ссылки или пути к существующим материалам;
- итоговые количества и финальное утверждение.

## Что пилот намеренно не делает

Пилот не создаёт новый рейтинг, не корректирует позиции вручную, не меняет пороги или формулы, не публикует «Топ-250» на сайте, не запускает массовую генерацию обзоров и не исправляет соседние части системы. Любые такие изменения должны выполняться отдельной задачей.
