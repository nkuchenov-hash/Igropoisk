# Управление центральной дизайн-системой

## Источники правил

- `assets/design-system.css` — библиотека визуальных компонентов.
- `config/design-system-components.json` — реестр разрешённых центральных компонентов и их ролей.
- `config/feature-modules.json` — реестр функциональных модулей и режимов проверки.
- `scripts/validate-central-design-system.mjs` — обязательная проверка архитектуры.
- `features/MODULE_RULES.md` — правила создания и постепенной миграции модулей.

## Что блокируется

Во всех новых строках CSS вне центральных файлов блокируются локальные цвета, фоны, границы, радиусы, тени, шрифты, состояния `hover/focus/active`, анимации компонентов и новые общие `--ig-*` токены.

В новых HTML- и JavaScript-шаблонах кнопки и поля обязаны использовать центральные классы. Локальные классы с признаками карточки, кнопки, поля, тега, панели или модального окна не принимаются без центрального компонента на том же элементе. Inline-стили и изменение `element.style` запрещены.

Каждый новый каталог в `features/` блокируется, пока он не зарегистрирован. Новый исполняемый модуль обязан работать в режиме `strict`; режим `metadata-only` оставлен только трём существующим служебным каталогам без интерфейса.

## Добавление нового компонента

1. Компонент или вариант создаётся в `assets/design-system.css`.
2. Его класс и роль добавляются в `config/design-system-components.json`.
3. Модуль добавляет класс в `centralComponents` своего `module.json`.
4. Локальный CSS содержит только композицию.
5. Проверки и production-деплой должны завершиться успешно.

## Защита production

`Design system check` проверяет изменения относительно базового commit. GitHub Pages повторяет ту же проверку перед публикацией. Ошибка дизайн-системы останавливает конкретный деплой и не изменяет уже опубликованный сайт.

Старые локальные стили не переписываются автоматически. Проверка запрещает добавлять новый локальный визуальный долг, а существующие разделы переводятся на центральные компоненты только отдельными согласованными задачами.
