# Игропоиск — стабильный автономный модуль новостей

**Статус:** READY / STABLE  
**Зафиксировано:** 2026-09-03  
**Режим дальнейших изменений:** только хирургические, изолированные правки

## Назначение

Новостной модуль автономно обнаруживает игровые новости, объединяет дубли одного события, оценивает значимость каждого события, формирует русскую публикационную версию, связывает новости с играми и публикует live-ленту в Yandex Object Storage.

Модуль новостей **не создаёт игровые страницы и не ждёт их создания**. Если подтверждённая игра ещё не имеет готовой страницы, новостной модуль передаёт её во временную очередь модуля сборки страниц и продолжает публикацию независимо.

## Зафиксированный production-поток

```text
источники
  ↓
сбор и нормализация
  ↓
дедупликация событий
  ↓
оценка значимости каждой новости
  ↓
русская редакционная версия
  ↓
финальная проверка качества каждой публикуемой новости
  ↓
разрешение связанных игр / хэштегов
  ↓
недостающие страницы → временная page-assembly queue
  │                         │
  │                         └→ отдельный модуль страниц
  ↓
публикация новостей без ожидания страниц
  ↓
атомарный snapshot + monthly archive в Object Storage
  ↓
live manifest
  ↓
главная + раздел «Новости»
```

Канонический workflow: `.github/workflows/news-pipeline.yml`.

## Жёсткий fail-open контракт

**Весь блок новостей не может быть остановлен внутренней логической проверкой.**

Правило уровня публикации:

- решение «публиковать / не публиковать» принимается для **отдельного события**;
- событие может не попасть в публичную выборку, если оно не прошло порог значимости/популярности;
- событие может не попасть в публичную выборку, если его русская редакционная версия не прошла финальную проверку качества;
- ошибка отдельного источника, изображения, хэштега, определения игры, очереди страниц, housekeeping, optional semantic refinement или диагностической проверки не имеет права остановить остальные новости;
- ошибки должны оставаться видимыми в health/report как `warning`, `degraded` или диагностическая ошибка;
- уже собранные пригодные новости продолжают путь до публикации;
- физическая недоступность Object Storage не удаляет существующую ленту: сайт продолжает читать последний успешно опубликованный snapshot, а новый цикл повторяет публикацию позже.

Запрещено возвращать архитектуру, где один дефект одной новости, игры или внешнего сервиса блокирует весь live snapshot.

## Отбор и значимость

Количество опубликованных событий **не фиксировано**. Система публикует столько отдельных событий, сколько реально прошло порог значимости и публикационную проверку качества.

Главные сигналы:

- число независимых источников, сообщающих об одном событии;
- авторитетность источников;
- свежесть;
- скорость одновременного распространения;
- обсуждаемость/общественный интерес;
- наличие сильного первичного официального источника.

Число независимых источников имеет нелинейный вклад с убывающей отдачей: переход от 1 к 2–4 источникам важнее, чем переход от 10 к 20. Четыре независимых источника — сильный практический сигнал широкой значимости, но **не механический обязательный минимум**.

Крупное официальное объявление может пройти порог до появления нескольких вторичных публикаций, если само событие достаточно значимо.

Ни pipeline, ни редакционная проверка, ни публикационный snapshot **не имеют фиксированной квоты количества новостей**. Любое ограничение количества карточек в конкретном интерфейсе, если оно когда-либо понадобится, является только настройкой интерфейса и не входит в контракт новостного pipeline.

## Русская редакционная версия и финальная проверка

Машинный перевод используется только как черновой слой и **не считается автоматически готовым редакционным текстом**.

Перед тем как событие остаётся публичным, его фактические `titleRu` и `summaryRu` проходят финальную проверку независимо от того, сколько всего новостей собрано в текущем цикле.

Финальная проверка обязана контролировать как минимум:

- сохранение названий игр, студий, компаний, сервисов и мероприятий;
- отсутствие буквального перевода собственных имён без явно заданного русского варианта;
- сохранение важных отрицаний и противоположностей смысла;
- отсутствие HTML-артефактов, оборванных латинских хвостов, повторов и типичных машинных дефектов;
- обычные production-требования к полноценному русскому заголовку и краткому тексту.

Если машинный черновик выглядит подозрительно, редакторский AI повторно формирует текст по английскому источнику и, когда возможно, по тексту самой статьи. Если исправленная версия всё равно не проходит проверку, **исключается только эта новость**. Остальная лента продолжает публикацию.

## Игры и хэштеги

Связь новости с игрой не должна ломать публикацию.

- Хэштег подтверждённой игры сохраняется и остаётся кликабельным.
- Если готовая canonical game page существует, хэштег ведёт на неё.
- Если готовой страницы ещё нет, хэштег ведёт на служебный маршрут `game/pending/?slug=...&title=...` с состоянием «Материал готовится».
- `game/pending/` **не является игровой страницей**, не является GameEntity и не проходит game-page publication gate.
- Наличие временного маршрута не означает, что страница готова: для такой игры сохраняются `pageReady: false` и `assemblyRequired: true`.
- Подтверждённая игра без готовой страницы записывается во временное page-assembly storage.
- Модуль страниц отдельно забирает эту очередь и создаёт полноценную страницу своим обычным процессом.
- Новостной workflow не запускает fast-page builder, не создаёт draft/page shell и не ждёт окончания page assembly.
- Ошибка записи в page-assembly queue не блокирует публикацию новостей.

Отдельное закреплённое identity-правило: слово `Ultimate` само по себе может быть частью канонического названия (`Super Smash Bros. Ultimate`) и не означает «edition». Edition определяется только явной формой вроде `Ultimate Edition`.

## Хранилище и публикация

Production runtime новостей читает контент через `features/news/content-api/`.

Основной backend — Yandex Object Storage:

- компактный live snapshot;
- стабильные monthly archives;
- cached media;
- live manifest, переключаемый после готовности нового snapshot.

Repository JSON — только аварийный fallback. Его устаревание не должно блокировать свежий сетевой сбор или unrelated deploy.

Порядок операций зафиксирован:

1. собрать и обработать новости;
2. проверить фактический публичный текст каждого события;
3. передать недостающие игры в независимую очередь;
4. опубликовать новый news snapshot и переключить live manifest;
5. только **после успешной публикации** выполнять prune старых snapshots и media GC.

Housekeeping никогда не находится перед live switch в качестве блокирующей зависимости.

## Изображения

Изображение — необязательный кэш.

- По возможности оно копируется в Object Storage.
- При отсутствии/ошибке используется фирменная заглушка.
- Ошибка изображения не блокирует текст новости.
- Media GC выполняется после публикации и не блокирует её.

## Автономность

- Schedule: каждый час, cron `23 * * * *`.
- Production-run использует актуальный `staging` как рабочий код pipeline.
- `cancel-in-progress: false`: новый цикл не отменяет предыдущий активный production-run.
- Pipeline не пишет сгенерированную новостную ленту в GitHub.
- Отчёты и health сохраняют диагностику каждого запуска.

## Freeze rule

Этот модуль считается завершённым стабильным механизмом. Дальше разрешены только **хирургические изменения**, которые сохраняют архитектуру и обратную совместимость.

Без отдельной прямой задачи на изменение архитектуры новостного модуля запрещено:

- заменять текущий pipeline новым параллельным pipeline;
- возвращать глобальный publication blocker для внутренних проверок;
- делать страницу игры, очередь страниц, хэштег, изображение, один источник или optional AI обязательной зависимостью всей ленты;
- заставлять новости напрямую создавать игровые страницы;
- убирать временный маршрут для хэштега только потому, что game page ещё не готова;
- превращать `game/pending/` в canonical game page или добавлять его в Game Registry;
- вводить фиксированную редакционную квоту количества новостей;
- привязывать успешность pipeline к любому фиксированному числу карточек или событий;
- перемещать storage cleanup/GC перед live publication;
- возвращать запись generated news в `main` как основной production storage;
- заменять Object Storage repository fallback'ом как основным backend;
- менять расписание, storage topology или module boundaries заодно с локальной правкой качества/источника/текста.

## Правило для будущих PR

Любая следующая правка должна быть минимальной и проверяемой отдельно. Типичные допустимые изменения:

- добавить/починить конкретный источник;
- улучшить дедупликацию конкретного класса событий;
- откорректировать вес одного сигнала значимости;
- исправить локализацию/текстовый дефект;
- исправить конкретную картинку;
- исправить конкретное game identity/linking правило;
- улучшить диагностику без изменения publication semantics.

Если для задачи требуется изменить orchestration, fail-open contract, storage model, page-assembly boundary или общую модель значимости — это уже **изменение стабильного модуля**, а не хирургическая правка, и должно выполняться отдельным осознанным PR.

Этот документ является основным freeze-контрактом текущего новостного инструмента.
